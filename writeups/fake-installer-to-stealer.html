From a fake game installer to a stealer

  • date: 2026-11-02
  • tag: malware
  • read: 12 min

summary

I got a 209 MB zip that claimed to be a game installer. It turned out to be three stages deep: a Node.js dropper, a Rust remote access trojan (RAT), and a C++ infostealer that calls itself "Mops Stealer V3". This is how I took it apart, what I got wrong along the way, and what a defender can use from it.

Everything below is static analysis, plus a few runs of the RAT inside an isolated VM. The stealer itself was never executed anywhere. Indicators are defanged, so replace [.] with . before you hunt for them.

how I stayed safe

  • Nothing from the zip was ever run on my own machine, so nothing was stolen from it.
  • Analysis ran on Linux with Python (pefile, capstone, unicorn), radare2 and Ghidra in headless mode.
  • The RAT ran only in a Windows 10 VM on an isolated network. The host dropped everything except the command server's ports, and DNS answered for one name only.
  • Anything received from the command server was treated as inert bytes.
note: to read the task queue I connected to the live command server with a throwaway fake client. I only read and never acted on what came back. Touching live attacker infrastructure can carry legal and safety risks, so think it through before repeating it.

the whole chain at a glance

Read it top to bottom. Each dashed vertical line is a program, and arrows are things one program sends or does to another. The detail for each numbered step is in the sections below.

stage 0: the bait

The zip is 209 MB and stored without compression. Most of it is real game content, such as FMOD audio banks, which makes it look legitimate. Next to that sits Setup.exe at 117 MB.

Setup.exe is a 64-bit Windows GUI program that contains the marker NODE_SEA_FUSE_fce680ab2cc467b6e072b8b5df1996b2. That is a Node.js single executable application, packaged with vercel/pkg, so a whole JavaScript program hides inside a normal-looking exe. The large overlay at the end is the bundled virtual filesystem.

stage 1: the dropper

I parsed the pkg manifest and carved out four files: index.js, package.json, payload.js (about 957 KB) and shell.js. A build path leaked in the process, C:\snapshot\5197705037_640_...\payload.js, and the number in it turned out to be the campaign ID.

Two things matter here:

  • A hidden PowerShell command adds Windows Defender exclusions for the temp folder and a few ProgramData paths, then runs gpupdate /force.
  • payload.js holds an object with a PayloadKey and about 956 KB of base64 in EncryptedBytes.

The key is 32 characters, so I assumed AES-256 and wasted time on CBC, ECB and CTR. All garbage. It is a plain repeating-key XOR. Once decoded, the output starts with MZ, which is a PE file. That file is dropped as C:\ProgramData\Windows\Microsoft\RuntimeBroker.exe, named after a real Windows process.

stage 2: the RAT

The dropped file is a 717,312 byte Rust program compiled on 2026-10-30. Statically it only imports KERNEL32.dll, with no networking at all. What it does import is LoadLibrary, GetProcAddress, VirtualAlloc, WriteProcessMemory and CreateProcess. That combination means it resolves its real APIs at runtime and can inject code, so the interesting calls never show up in the import table. It also has a .strenc section for string encryption.

cracking the strings

There are two custom string ciphers. The main one rotates each byte right by a position-dependent amount and XORs it with a keystream. Wide strings need every other byte first:

def ror8(x, n):
    n &= 7
    return ((x >> n) | (x << (8 - n))) & 0xFF

def decrypt(ct):
    return bytes(ror8(c, (i % 7) + 1) ^ ((i * 13 + 197) & 0xFF)
                 for i, c in enumerate(ct))

That decoded 30 or more strings and the whole config block, which is set up by a chain of 13 small functions:

I searched the decoded and plain strings for any second exfiltration channel, such as a Discord or Telegram webhook, Pastebin, FTP or another domain. There is none. The RAT has no theft logic of its own. It is a loader that asks the server what to run next.

A side note on tooling: I wanted r2ghidra for decompiling, but it would not build against radare2 6.0.5. I dropped it and used radare2, Unicorn and Capstone instead, and later Ghidra headless.

the command server

The domain resolves to 185[.]235[.]128[.]170. Port 3000 is a decoy Express app that redirects everything to Google. The real services are on 406 and 408.

Port 406 is a WebSocket. The server sends ping and the client answers pong. The client registers with ready;5197705037;, the server asks getinfo, and the client replies with info;<host>;<user>;<os>;<arch>;<ver>;. Then it gets its tasks:

task;createtask;Stealer;task_id;ggvk8x_06r3;version;1.0.1
task;createtask;Stealer;task_id;hwhf8d_4ngg;version;1.0.1
task;createtask;Stealer;task_id;xnqwf7_0s1z;version;1.0.1

The task carries no instructions beyond a module name, so all the stealing lives in the module. The RAT downloads it over HTTP on port 408 and then runs it. The format strings hint at a chunked transfer, though the single download I captured came back as one response.

the 403 wall, and a wrong guess

Downloading the module myself always returned 403 Access denied. I tried different User-Agents, composite paths, a held-open session from the same IP and more, and some attempts hit a rate limit. I then traced the User-Agent through four nested functions in the RAT and found it is a field of a runtime context object, not a constant, so static analysis could never give me the value.

correction: early on I claimed the server only serves a task to the victim it was assigned to. That was wrong. A brand-new fake client got three tasks immediately, which only makes sense if they are broadcast to every bot. The 403 gate is something else, and I never worked out what.

getting the stealer without running it

Since I could not download the module, I let the RAT fetch it inside the lab VM and recorded the traffic. The catch was that the RAT kept exiting before it did anything. Procmon showed nothing because the decision is made in memory.

Breaking on ExitProcess in x64dbg and following references in radare2 led to one function. It asks Direct3D9 for the graphics adapter name and compares it with a blocklist, and it exits quietly on a match. The list covers the usual virtual GPUs (VMware, VirtualBox, QXL, Virtio, Hyper-V, Parallels, Citrix, the Windows software renderer) and also anyrun, which likely explains why public sandboxes saw nothing. A second function checks the CPUID hypervisor bit.

Spoofing the registry did not work, because the software renderer always reports its own name. In a working copy of the RAT I patched the two conditional jumps behind the GPU check so they always skip the exit. The patched RAT then beaconed, got its task, and sent GET /task/Stealer. The reply was a 200 OK with application/octet-stream, 1,120,256 bytes, starting with MZ. I exported it from the packet capture. It was never run.

stage 3: the stealer

It is a 64-bit C++ DLL compiled on 2026-10-28. It is not packed and it has no exports, which fits being loaded reflectively by the RAT. Unlike the RAT its strings are plain text, so the target list reads like a menu. It labels its own report - Mops Stealer V3: and uses the mutex Global\StealerLib.

what it goes after

  • Browsers: about 46 Chromium and Gecko families. Saved logins, cards and autofill, cookies, Local State and history.
  • Crypto: desktop wallets and wallet browser extensions, found by extension ID.
  • Sessions: Telegram, Discord tokens, Steam and Viber.
  • Apps and files: FileZilla, several VPN configs, AnyDesk, game launchers, a generic file grabber and a screenshot.
  • Host report: OS, CPU, GPU, hardware ID, country and an affiliate or build ID.

the encryption detail I liked

It knows three ways to recover a browser's master key: the old DPAPI key, the newer app-bound key with two DPAPI layers, and an unwrap through the Windows key storage provider using a persistent key called Google Chromekey1. That last one is how it gets past Chrome's app-bound protection.

What surprised me is that it never decrypts anything itself. I looked for AES tables, AES-NI instructions, carry-less multiply and a BCrypt import, and found none. My conclusion, which is an inference and not something I saw on the server, is that it ships the unlocked master keys plus the raw encrypted stores and leaves the final AES-GCM step to the operator's side.

how the loot leaves

Everything is packed into a ZIP in memory, and nothing is written to disk. Then the stealer sends it straight to the C2 on port 1488, using its own raw TCP socket with no TLS and no HTTP:

victim -> server   <C: volume serial>stealer;\n
server -> victim   reply containing "auth_ok"   (no auth_ok: close, no upload)
victim -> server   8-byte big-endian length + ZIP bytes
victim             closesocket, then TerminateProcess(self, 0)

The last step matters for defenders. After one upload it kills its own host process with exit code 0. It has no loop, no self-delete and no persistence of its own. Persistence belongs to the RAT. One caveat: the stealer calls TerminateProcess on its own process, so the RAT only survives if it ran the stealer in a separate process that it spawned or injected into. That fits the RAT's CreateProcess and injection imports, but I did not fully reverse the loader, so which process dies is an inference, not something I confirmed.

correction: my first draft said the upload port was 408. The number 0x198 in the decompiled code looked like a port, but it is the size of the WSAStartup buffer. The real port is 1488, which I confirmed from the string passed to getaddrinfo and from a connection attempt to that port that my lab firewall dropped. So 408 is where the RAT downloads modules and 1488 is where the stealer uploads loot.

detection ideas

These come from my analysis and I have not tested them against production telemetry.

  • Defender exclusions: alert on Add-MpPreference -ExclusionPath in PowerShell logs, and on exclusion changes for temp or ProgramData paths.
  • Masquerade: the real RuntimeBroker.exe lives in System32. One under ProgramData is a strong signal.
  • Odd installer: a game "installer" that is a Node.js single executable app, which the fuse marker above gives away.
  • Network: outbound traffic to the C2 on 406, 408 or 1488, or raw TCP carrying a short line that ends in stealer;.
  • Browser kills: a non-browser process force-closing every Chrome, Edge or Firefox instance moments before credential files are touched. The stealer does this to unlock their databases.
  • Mutexes: Global\StealerLib, and Global\RuntimeBrokerAds, which the stealer checks for before it runs.
  • Behaviour: an unsigned process opening the Microsoft Software Key Storage Provider and the Google Chromekey1 key.

On VirusTotal at the time, the domain was flagged by 8 of 92 vendors and Setup.exe by 4 of 69, and the zip had been uploaded only about 16 hours earlier. The RAT was not there, which fits it being an in-memory blob that nobody uploads.

what I still do not know

  • What the collector on port 1488 does with the ZIP, and how it decides on auth_ok.
  • The full pool of tasks the operator can send, since I only ever saw the stealer task.
  • What the 403 gate on port 408 actually checks. I got the module by detonation, not by beating it.

takeaways

Most of my time went on wrong guesses, like AES for an XOR, a task list I read as per-victim that was really a broadcast, and a port that was a buffer size. Writing the corrections down mattered as much as the final answer.
